# H01 — Data platform (DuckDB + dbt) + DataHub ingestion

**Milestone:** M1 · **Depends on:** H00 · **Prereqs env:** none to pass verify
(`DATAHUB_GMS_URL`/`DATAHUB_TOKEN` used only if present).

## Goal
Build a real, small retail data platform: DuckDB warehouse + a dbt project (raw → staging →
marts) seeded from a fixed dataset, plus DataHub ingestion recipes that push table + column
lineage, schemas, owners, and query history into DataHub. This is the platform the chaos
engine will break and the agents will heal — it must be genuinely real, not mocked.

## Context recap
The dbt project lives in the **separate `kavach-demo-pipeline` repo** so the Fixer (H06) can
open real PRs against it. This handoff (in the `kavach` repo) provides: (a) the seed data +
fixtures under `data/`, (b) the DataHub ingestion recipes under `data/ingestion/`, (c) a
`data/pipeline.py` runner that builds the DuckDB warehouse and runs dbt, and (d) a bootstrap
of the `kavach-demo-pipeline` dbt project content under `data/demo_pipeline_seed/` that H06
will push. Keep everything deterministic (fixed seeds).

## Domain: fictional retail
Entities: `orders`, `order_items`, `products`, `suppliers`, `customers`. Marts:
`mart_daily_revenue`, `mart_supplier_reliability`, `mart_demand_features` (feeds the ML model
in H02). Include an intentionally realistic dependency chain so blast-radius is interesting:
`raw.orders` → `stg_orders` → `mart_daily_revenue` → (dashboard entity) and
`raw.order_items`+`stg_products` → `mart_demand_features` → (ML model in H02).

## Deliverables
- `data/seeds/*.csv` — deterministic seed CSVs for all raw tables (~500–2000 rows each,
  generated by a fixed-seed script `data/generate_seeds.py`; commit both the generator and
  the CSVs).
- `data/demo_pipeline_seed/` — a complete dbt-duckdb project (dbt_project.yml, profiles
  template, `models/staging/*.sql`, `models/marts/*.sql`, `schema.yml` with column
  descriptions + tests). This is the content H06 pushes to `kavach-demo-pipeline`.
- `data/pipeline.py` — `build()` loads seeds into `warehouse.duckdb` and runs `dbt build`
  against it; `--target` supports `dev`. Idempotent.
- `data/ingestion/datahub_recipe.dbt.yml` — DataHub dbt ingestion recipe (source: dbt
  artifacts `manifest.json`/`catalog.json`; sink: DataHub REST from `DATAHUB_GMS_URL`).
- `data/ingestion/datahub_recipe.duckdb.yml` — DataHub SQL/DuckDB ingestion for raw tables.
- `data/ingestion/queries_seed.py` — seeds representative query-history entries into DataHub
  (so Investigator's `get_dataset_queries` root-cause is real). If DataHub unset, writes them
  to `data/fixtures/queries.json` instead.
- `data/fixtures/` — recorded DataHub payloads (schemas, lineage, sample queries) so
  everything works offline / in CI without a live DataHub.
- `backend/app/datahub/fixtures.py` — loader for the fixtures (used by tests + replay).
- `data/README.md` — how to run the pipeline + ingestion.
- Tests: `backend/tests/test_pipeline.py` (build produces expected tables + row counts,
  deterministic), `data/tests/` dbt tests wired via `dbt build`.

## Step-by-step
1. Write `generate_seeds.py` (fixed `random.seed(42)` / numpy seed) → emit CSVs.
2. Author the dbt project under `data/demo_pipeline_seed/` with staging + marts + `schema.yml`
   (rich column descriptions/owners/tags — these become DataHub metadata).
3. Write `pipeline.py` to load seeds → DuckDB and run `dbt build`; assert marts exist.
4. Write ingestion recipes; run them if `DATAHUB_GMS_URL` set, else generate fixtures.
5. Capture fixtures (schemas, lineage edges, queries) into `data/fixtures/`.
6. Tests green; run this handoff's `verify.sh`; commit `H01: data platform + ingestion`.

## Definition of done
`verify.sh` exits 0: seeds generate deterministically, `pipeline.py build` creates all marts
in DuckDB, dbt tests pass, ingestion recipes are valid YAML/parse, fixtures exist and load,
and pytest is green. Live DataHub ingestion is exercised only when env is set (else skipped,
not failed).
